# Spec 074 — Research for safe Generation III event save editing

## Intent and current boundary

This spec records the research and requirements for Generation III event save editing. The delivery can put the Eon Ticket, Old Sea Map, AuroraTicket, and MysticTicket directly into the **Key Items** pocket. Pure byte tools work on private buffers; the backend delivery service owns the eventual canonical write. Do not infer that four free slots are always required: already-owned items do not need a second slot.

The encounter catalog in `apps/packages/pokemon-gen3-event-encounters.json` names destinations and species and records title-specific Key Item IDs, layouts, and the reviewed item/flag grant recipe for Ruby, Sapphire, Emerald, FireRed, and LeafGreen. The pure package materializer and backend delivery service consume it. The catalog does not itself define safe delivery timing, ROM verification, leases, or durable receipts. Ruby and Sapphire list Eon Ticket; Emerald lists all four event items; FireRed and LeafGreen list MysticTicket and AuroraTicket.

The original Emerald island scripts place Deoxys (level 30) on Birth Island and both Lugia and Ho-Oh (level 70) on Navel Rock. FireRed and LeafGreen also contain those two item-gated island destinations and their encounters. The backend grant is connected, but these in-game outcomes still await disposable-save verification.

## Research findings

### Existing project code

- `apps/packages/pokemon-gen3-save-validation.mjs` requires a 128 KiB initialized save, checks each of the 14 sectors in each copy, validates sector IDs, signatures, checksums and save index, and selects the valid copy with the highest save index. It currently chooses the first copy on an equal index; an event writer should explicitly handle equal-index disagreement before changing bytes.
- `apps/packages/pokemon-gen3-adapter.mjs` already reads event flags for transfer capabilities and writes Party/PC Pokémon to a private `Buffer`, recalculating sector checksums. The event tool should reuse the save-copy/section machinery or extract a common small primitive, not introduce a second full save parser.
- `apps/packages/pokemon-gen3-save-capabilities.json` contains title-specific event flag and variable bases for existing transfer checks. It has no Bag, PC item, security-key or event-delivery profile.
- The backend `saveStore.put` path uses a revision check and atomic file replacement. Pokémon Hub flushes already hold source leases. Spec 070 invalidates incompatible runtime states after a Hub materialization. Event writes must integrate with those same ownership, revision, snapshot, and recovery rules; an offline file edit alone would let a player upload stale save bytes later.

### PKHeX as a reference, not a dependency

The upstream PKHeX repository declares GPL version 3. `SAV3E`, `SAV3RS`, `SAV3FRLG`, their `PlayerBag3*` classes, and `SaveBlock3Large*` confirm that Gen III has distinct title layouts and dedicated inventory/event-flag handling. PKHeX's Bag definitions report 20 Key Item slots in Ruby/Sapphire, 30 in Emerald and FireRed/LeafGreen, and separate PC item inventories (50 slots for Ruby/Sapphire/Emerald, 30 for FireRed/LeafGreen). The original Emerald decomp independently defines `BAG_KEYITEMS_COUNT` as 30. Emerald and FireRed/LeafGreen Bag quantities use a security key; their PC item quantities do not. Ruby/Sapphire's Bag class does not take a security key. Layout and encoding figures still require independent real-save and emulator corroboration; the backend integration alone does not establish in-game behavior.

Do not copy or translate PKHeX implementation code, tables, or tests into this project. Use it to identify questions and independently derive the minimal facts from original-game behavior, the pret decompositions and controlled save fixtures. The license implications of copying even a small adapted script require separate review. Small Node modules in `apps/packages/` fit the existing validator, adapter, save store, and backend.

### Original-game event scripts and inventory

- The original Emerald item table sets `.pocket = POCKET_KEY_ITEMS` for **all four**: Eon Ticket, Old Sea Map, AuroraTicket and MysticTicket. They are not ordinary Bag items. The Key Items pocket has a finite 30-slot capacity. It may normally have room, but a writer must verify that assumption against the actual save rather than overwrite an occupied slot.
- In Emerald, the Old Sea Map, AuroraTicket, and MysticTicket Mystery Gift scripts check whether the item or encounter was already obtained, check free space in the Key Items pocket, give one item, and set both a received-item flag and a ship-destination flag. Their full-Bag text tells the player to move something to the PC and return. This confirms both that adding an item ID alone is insufficient and that the game's own delivery path handles a full pocket.
- Each Bag/PC item slot has a 16-bit item ID and 16-bit quantity. The Bag and PC are separate inventories. A ticket stored in the PC should not be assumed to satisfy a Bag item check at the harbor; verify the actual port script for each title.
- Key Item capacity concerns the dedicated pocket, not arbitrary free space elsewhere in the Bag. Space required for an operation is the number of *missing* unique items that must be placed in that pocket. Already-owned items must not be duplicated. Before any edit, inspect Bag and PC for each requested item, relevant received/destination/encounter flags, and prerequisite progression. If there is insufficient room, reject the proposed write without modifying the save; this is an integrity guard, not an alternative delivery feature.
- The Eon Ticket path differs: Ruby and Sapphire have fixed opposite-island species, while Emerald's island species depends on the selected roaming Pokémon. Its receipt and ship access mechanism must be researched independently; do not reuse Emerald's three Mystery Gift flag recipe by assumption.

## Automatic delivery after game completion

### Eligibility and event set

The product rule is automatic, once per profile and game, only after a completed player close. Ruby/Sapphire qualify when `FLAG_SYS_GAME_CLEAR = 0x804` proves the League and Champion were beaten; the backend then enables their National Dex and grants Eon Ticket with its event flags in one isolated candidate. This substitutes for the unavailable cross-game trade path. Ruby/Sapphire do **not** require an already-unlocked National Dex. Emerald still requires both League completion (`FLAG_SYS_GAME_CLEAR = 0x864`) and its in-game National Dex upgrade from Birch; FireRed/LeafGreen retain their separate three-part gate. Do not infer League completion from badges, the last Elite Four battle, a UI state, or the National Dex alone. The existing `pokemonGen3Adapter.inspect(...).transferCapabilities.nationalDexUnlocked` checks each title's magic byte, persistent flag, and work value together; use it to avoid changing a complete existing Ruby/Sapphire unlock. Never set the game-clear flag on the player's behalf.

The original Ruby/Sapphire `EnableNationalPokedex` routine writes `nationalMagic = 0xDA`, `VAR_NATIONAL_DEX = 0x0302`, and `FLAG_SYS_NATIONAL_DEX = 0x836`, then sets Pokédex `mode = 1` (National) and `order = 0`. The logical save locations are small block `0x1A` (magic), `0x19` (mode), `0x18` (order); large block `0x13CC` (little-endian variable) and `0x1220 + floor(0x836 / 8) = 0x1326`, bit 6 (flag). These are section-mapped offsets, never absolute `.sav` addresses. The pure Ruby/Sapphire editor changes only these bytes/bits in the selected valid copy, repairs only touched section checksums, and verifies the adapter reports National Dex unlocked. If already unlocked, it preserves the player's current Pokédex mode/order and returns equal bytes. The game routine also resets `sLastSelectedPokemon` and `sPokeBallRotation`; the decomp defines those as runtime scroll/display state, so the offline save editor does not write extra fields for them. Emerald and FireRed/LeafGreen National Dex bytes remain untouched.

For the currently cataloged events, the eligible bundle is Eon Ticket for Ruby/Sapphire; Eon Ticket, Old Sea Map, MysticTicket, and AuroraTicket for Emerald; and MysticTicket plus AuroraTicket for FireRed/LeafGreen. The corresponding item IDs come from `pokemon-gen3-event-encounters.json`. The user's product rule grants all cataloged Emerald events on a verified supported Emerald ROM, including Old Sea Map; historical distribution regions are context, not a delivery restriction. The backend verifies the original ROM bytes against its catalog SHA-256 and requires a compatible title/layout registration. The presence, absence, validity, or hash of an optional IPS does **not** gate save event delivery: patch resolution belongs to the runtime integration, while save editing uses the verified ROM's declared save layout and validates the candidate independently. The applied patch hash is logged only as diagnostic context. The earlier unconditional IPS exclusion silently prevented delivery on the shipped Emerald ROM, which has a registered 94-byte IPS. If a future IPS changes the game's save layout, the ROM's save-layout contract and core save pipeline must be updated together; the event writer must not infer a new layout from an IPS file. Exact ROM revision/language and in-game behavior still need disposable-save confirmation. Unknown, unverified, or mismatched original ROM identity skips the optional delivery while normal save/load continues. FireRed/LeafGreen add a third eligibility condition: Celio's Network Machine must be restored after the Ruby and Sapphire gemstones are installed. Their gate is therefore **League complete AND National Dex unlocked AND Network Machine restored**; the machine condition does not replace either previous condition. The Vermilion City ferry has an additional Sevii story-scene prerequisite for offering event destinations; delivery must not fabricate that story variable or promise immediate ferry access if the player has not progressed through it.

### FireRed/LeafGreen progression bytes and read path

These are logical save-block offsets, not fixed CPU RAM addresses or absolute `.sav` positions. Resolve the validated newest save copy's section map first; physical sector order rotates. In the FireRed/LeafGreen decomp, `SaveBlock1.flags` begins at `0x0EE0` and `SaveBlock1.vars` at `0x1000`; `SaveBlock2.pokedex.nationalMagic` is at small-block offset `0x1B`. The relevant fields are:

| Condition | Original-game symbol/value | Logical location | Read rule |
| --- | --- | --- | --- |
| League complete | `FLAG_SYS_GAME_CLEAR = 0x82C` | large block `0x0EE0 + floor(0x82C / 8) = 0x0FE5`, bit 4 | Flag must be set. |
| National Dex | `nationalMagic = 0xB9` | small block section 0, offset `0x1B` | Byte must equal `0xB9`. |
| National Dex | `FLAG_SYS_NATIONAL_DEX = 0x840` | large block `0x0FE8`, bit 0 | Flag must be set. |
| National Dex | `VAR_NATIONAL_DEX = 0x404E`, value `0x6258` | large block `0x1000 + (0x404E - 0x4000) * 2 = 0x109C` | Little-endian `u16` must equal `0x6258`. |
| Network Machine restored | `FLAG_SYS_CAN_LINK_WITH_RS = 0x844` | large block `0x0FE8`, bit 4 | Flag must be set. |

Large-block offsets `0x0FE5`, `0x0FE8`, and `0x109C` resolve to logical section 2 at local offsets `0x65`, `0x68`, and `0x11C`; the physical `.sav` offset is that section's mapped sector start plus the local offset. `pokemonGen3Adapter.inspect(saveBytes, layout).transferCapabilities` returns `nationalDexUnlocked` from all three National Dex fields and `networkMachineRestored` from `0x844` for both FireRed and LeafGreen. The generic `readPokemonGen3Flags(saveBytes, title, [0x82C])` reads the League bit from the same validated section mapping. The pure `inspectPokemonGen3EventEligibility(saveBytes, pokemonSaveTitle)` package function combines these readers against a validated, unambiguous save copy and returns `{ gameClear, nationalDexUnlocked, networkMachineRestored, eligible }`. Ruby/Sapphire `eligible` depends on game clear; other titles retain their National Dex requirement. The backend delivery service calls it against one canonical save revision. `FLAG_GOT_RUBY` and `FLAG_RECOVERED_SAPPHIRE` represent earlier FireRed/LeafGreen story steps; they are not substitutes for the final machine flag. The event grant reads these progression fields; only the reviewed Ruby/Sapphire National Dex upgrade may set progression fields, and it never sets game clear.

The original Celio script calls `IsNationalPokedexEnabled` before asking for the Ruby, then sets `FLAG_SYS_CAN_LINK_WITH_RS` only after accepting the Sapphire, activating the machine, and finishing the scene. Link initialization also reads National Dex status and `FLAG_SYS_CAN_LINK_WITH_RS` independently. In this decomp, `RS` refers to the Hoenn games Ruby/Sapphire; FireRed/LeafGreen are themselves Generation III games, despite revisiting the Generation I region.

### Delivery recipe and consistency

The backend orchestrator must use a reviewed per-title/per-event recipe that pairs each item with the flags needed for in-game travel. The original sources distinguish **global distribution-menu unlocks**, **item receipt**, **ship access**, **first display**, and **encounter completion**. They must not be treated as interchangeable:

| Title | Flag | ID | Original behavior | Delivery policy |
| --- | --- | ---: | --- | --- |
| Ruby/Sapphire | `FLAG_SYS_EXDATA_ENABLE` | `0x84C` | Enables the Mystery Event title-menu entry. Ruby/Sapphire have no separate Emerald-style Mystery Gift flag. | Include as the title's distribution-menu unlock, then verify its behavior on a disposable save. It is not a harbor requirement. |
| Ruby/Sapphire | `FLAG_SYS_HAS_EON_TICKET` | `0x853` | Set by original Eon Ticket gift/record mixing; checked along with the Bag item and game-clear flag at Lilycove Harbor. | Set with Eon Ticket. |
| Emerald | `FLAG_SYS_MYSTERY_EVENT_ENABLE` | `0x8AC` | Unlocked by the questionnaire's Mystery Event phrase; also checked for saved Wonder News rewards. The normal title-menu selection shown in `main_menu.c` does not consult it. | Include as a separate global unlock requested for the event bundle, after confirming no unwanted behavior on disposable saves. It is not a harbor requirement. |
| Emerald | `FLAG_SYS_MYSTERY_GIFT_ENABLE` | `0x8DB` | Unlocked by the questionnaire's Mystery Gift phrase; controls appearance of Mystery Gift on the title menu. | Include as the Mystery Gift menu unlock requested for the event bundle. It is not a harbor requirement. |
| Emerald | `FLAG_ENABLE_SHIP_SOUTHERN_ISLAND` | `0x8B3` | Eon Ticket plus this flag enables Southern Island in the ferry selection. | Set with Eon Ticket. |
| Emerald | `FLAG_ENABLE_SHIP_FARAWAY_ISLAND` | `0x8D6` | Old Sea Map plus this flag enables Faraway Island. | Set with Old Sea Map. |
| Emerald | `FLAG_ENABLE_SHIP_NAVEL_ROCK` | `0x8E0` | MysticTicket plus this flag enables Navel Rock. | Set with MysticTicket. |
| Emerald | `FLAG_ENABLE_SHIP_BIRTH_ISLAND` | `0x8D5` | AuroraTicket plus this flag enables Birth Island. | Set with AuroraTicket. |
| Emerald | `FLAG_RECEIVED_OLD_SEA_MAP` | `0x13C` | Original Mystery Gift script sets it when giving the item. | Set with Old Sea Map to mirror completed receipt. |
| Emerald | `FLAG_RECEIVED_MYSTIC_TICKET` | `0x13B` | Original Mystery Gift script sets it when giving the item. | Set with MysticTicket to mirror completed receipt. |

| FireRed/LeafGreen | `FLAG_RECEIVED_AURORA_TICKET` | `0x2A7` | Original distribution script sets it when giving the item. | Set with AuroraTicket to mirror completed receipt. |

The Emerald and FireRed/LeafGreen ferry scripts explicitly test each Bag item together with its ship flag. Global Mystery flags are separate menu unlocks. The Emerald questionnaire requires the ordinary Pokédex flag before unlocking either Mystery menu; Emerald's National Dex prerequisite for automatic delivery already implies progression past that point. The orchestrator must not manufacture Emerald's ordinary Pokédex or National Dex flags. Emerald's first-display flags (`FLAG_SHOWN_EON_TICKET` `0x1AE`, `FLAG_SHOWN_AURORA_TICKET` `0x1AF`, `FLAG_SHOWN_OLD_SEA_MAP` `0x1B0`, `FLAG_SHOWN_MYSTIC_TICKET` `0x1DB`) and FireRed/LeafGreen's first-display flags (`FLAG_SHOWN_MYSTIC_TICKET` `0x2F0`, `FLAG_SHOWN_AURORA_TICKET` `0x2F1`) are set by the ferry flow and must remain untouched. Arrival, defeated, caught, and encounter puzzle flags must also remain untouched so each island plays normally. Ruby/Sapphire's harbor additionally rejects an already encountered Lati event; delivery must not clear that progress flag to force another encounter.

This table is a researched **candidate recipe**, not a claim that Mystery menus are technically necessary for ferry travel. The backend currently uses the recipe; the title-menu effect of global unlocks and the destination/encounter behavior still need confirmation on disposable saves and by the user in the actual game. An optional enhancement failure must not block core save/load. Do not substitute Emerald flag numbers in Ruby/Sapphire. The generic flag writer remains separate from the inventory writer and receives only these reviewed IDs from a trusted caller.

### Emerald Match Call default

For the current single-user product, the same eligible Emerald close-time recipe also clears `FLAG_HAS_MATCH_CALL` (`0x12F`) by default. In the original Emerald decomp, `TryStartMatchCall` checks this flag before its step, time, chance, map, and registered-trainer checks, so clearing it suppresses random incoming trainer calls without deleting contacts. The PokéNav menu uses the separate `FLAG_ADDED_MATCH_CALL_TO_POKENAV` (`0x130`), which must stay unchanged. This is not a complete mute: step-triggered story calls use separate flags and scripts. Clearing `FLAG_HAS_MATCH_CALL` also stops registration of newly fought trainers until restored. Preserve all contact flags and story-call flags; a later user preference may choose a more selective mechanism.

Record the Emerald-only clear operation in the catalog beside the event flag recipe. Apply it with the existing generic flag editor after Emerald's normal progression gate, in the same candidate as tickets and unlocks. The independent candidate validator must confirm the flag is clear and allow only its one bit to change in the clearing direction. Include the cleared flag ID in bounded commit diagnostics. Advance the Emerald receipt recipe version so profiles already carrying the prior event receipt receive this safe, backed-up migration on a later completed player close or the manual reconciliation endpoint. Other games keep their existing recipe version and behavior. Normal later saves preserve the receipt, so this default is applied once per save lineage; a later preference design must define how it interacts with receipt state.

### Pure package materializer for the complete event recipe

Store the reviewed flag IDs in the Generation III event JSON alongside the item IDs: `globalUnlockFlagIdsByTitle` for the title's Mystery menu flags and `grantFlagIdsByTitle` on each event for its ship and received-item flags. The JSON remains the single declarative source for the event recipe. The small package orchestrator, `materializePokemonGen3EventGrant(saveBytes, pokemonSaveTitle, eventIds)`, selects only supported catalog events for the trusted title, rejects duplicate/unknown event IDs or an empty request, and returns a new validated 128 KiB buffer only when `inspectPokemonGen3EventEligibility` accepts the same input save. A failed progression gate raises `SAVE_EVENT_INELIGIBLE` before any candidate edit. It does not write a file, set a receipt, choose a safe delivery time, or take a lease; the backend delivery service owns those requirements.

After event-request validation and the progression gate, the materializer first applies Ruby/Sapphire's National Dex editor when needed, then calls the independent Key Items tool for the selected title-specific IDs and the independent flag tool with the de-duplicated union of the title's global Mystery unlocks and selected ship/receipt flags, plus Emerald's reviewed Match Call clear operation. An eligibility, item, or flag validation failure returns no candidate and leaves the caller's bytes unchanged. Verify that the output has every requested item in Key Items, every required recipe flag set, Emerald's Match Call flag clear, and Ruby/Sapphire's full National Dex predicate when applicable. Game clear, Emerald/FireRed/LeafGreen progression, first-display, arrival, defeated, caught, puzzle, and unrelated flags remain untouched. An already-present item/flag is accepted idempotently. This makes the global unlocks part of the same proposed event save edit, without coupling the generic flag and inventory tools to each other. Tests exercise full and partial Emerald bundles, Ruby/Sapphire and FireRed/LeafGreen, all eight FireRed/LeafGreen progression combinations, partial National Dex state, rejected early grants, duplicates and unsupported events, full-pocket/PC failures, idempotence, and unchanged original bytes.

Preflight the whole eligible bundle against one canonical revision: check progression, existing Bag and PC items, already-set flags, capacity for missing items, save-copy ambiguity, and ROM policy. Existing correct items or flags count toward completion without duplication. A ticket only in the PC or a malformed/ambiguous save defers delivery and records a bounded diagnostic; it does not mark delivery complete. Apply missing items and flags to a private copy, verify exact byte changes, checksums, the final Bag contents and all required flags, and publish the combined candidate through **one** revision-checked save-store write. Failed preflight makes no save or marker change. No partial event bundle is reported as delivered.

### Trigger, ownership, and durable receipt

For this backend slice, “isolated validation” means materializing into a private buffer and loading that candidate through the independent Gen III save inspector before publishing it; the backend has no emulator core and does not claim to boot a ROM. The candidate validator compares the original and candidate at byte level, allowing only requested Key Item slots, requested event-flag bits, Ruby/Sapphire's reviewed National Dex fields when the original lacks the unlock, and affected section checksums to differ. It rechecks checksums, active copy identity, title-specific eligibility, Bag contents, required flags, and Ruby/Sapphire's complete National Dex predicate. Emerald and FireRed/LeafGreen progression must remain equal. A disposable original save and its metadata must be durably backed up before any canonical replacement, with a per-save journal that can roll back an interrupted save/metadata pair. Keep this backup for the user's later in-game verification. A failed isolated validation must leave the canonical save and receipt untouched.

An unfulfilled profile/game is considered only after the user closes the player and the final save sync succeeds, once the title-specific progression gates are true. The frontend waits for the player's close acknowledgement and final save upload, then releases the player lease with `closeCompleted: true`. The backend schedules the optional attempt after returning that successful lease-release response, and only when `preserveRecovery` is false. A lease release without explicit close completion, including interruption or an older client, cannot trigger the grant. Ruby/Sapphire's National Dex enablement and Eon Ticket delivery happen in the same candidate and one canonical save-store transaction; neither is written during live play or in a separate earlier save revision. The package service checks for another player or Pokémon Hub lease before preparing the candidate and again inside the save-store lock before committing. It applies the existing revision/fence checks and Spec 070 runtime-state invalidation marker. If no safe window exists, it defers delivery until a later completed player close. The optional delivery never rejects an otherwise valid save upload, profile/lease acquisition, or launch. A launch may proceed without the event enhancement if the safe attempt fails. Initial startup and Pokémon Hub-only lease release do not independently trigger delivery in this slice.

Backend diagnostics for each completed close must record whether delivery was scheduled, the final attempt status and reason, and, for a supported save, the title, verified ROM hash, applied patch hash if any, save revision, and League/National Dex/Network Machine gate booleans. A successful commit must record the old/new revision and save hashes, preimage backup filename, requested event IDs, **actually inserted** item IDs, and **actually enabled** flag IDs. These are bounded identifiers and integrity metadata, never raw save bytes, trainer identity, Pokémon data, or a full inventory dump. The default container logger must not filter these event diagnostics. A returned `unsupported-rom`, `pending-progression`, `deferred-lease`, `already-delivered`, or `skipped` result must be observable; a resolved promise with a non-delivery status is not an exception and must not disappear in an ignored `setImmediate` return.

The durable receipt lives in the canonical save's backend metadata, which is already scoped by **profile ID and game ID**; it records verified ROM SHA-256, recipe version, event IDs, resulting save revision/hash, delivery time, and the preimage backup filename. This is backend-owned state, not a browser flag. `saveStore.put`, metadata validation, and fence advancement preserve the receipt through normal later in-game saves. Once all eligible events are recorded as delivered, later attempts use the cheap receipt lookup rather than reparsing the Bag. The backend state archive includes the receipt alongside canonical save bytes and profile state; the event preimage is also retained as a separate backup file.

### Manual reconciliation of existing saves

An operator may call `POST /api/ops/gen3-events/deliver` with the same Bearer token required by `POST /api/ops/backups/backend-state`; other HTTP methods return `405`. There is no public UI or automatic startup scan. The request is synchronous and serial within one backend process: a concurrent batch on that process receives `409`. Across backend processes, the save-store lock, lease, revision/fence checks, and durable receipt prevent overlapping writes to one save. Before enumerating or changing candidates, the backend must finish a full backend-state backup with reason `gen3-event-delivery`; missing backup configuration, authorization failure, or backup failure prevents every event edit. An unreadable canonical save that prevents a complete batch backup also aborts the run before edits. This batch backup supplements the existing durable, verified per-save preimage and journal; the per-save backup remains mandatory for each actual mutation and captures the exact current save even if other profiles change during the batch.

The runner enumerates canonical saved profile/game pairs, checks that each still has a backend-owned profile, and calls the same event-delivery service used after a completed player close. It never edits bytes directly. That service re-reads each save and verified ROM identity and enforces the receipt, progression, lease, revision/fence, candidate validation, preimage backup, and readback rules at the moment of the attempt. A live player or Pokémon Hub lease yields `deferred-lease`; no live save is modified. One unsupported, ineligible, malformed, or failed save does not prevent inspection of later pairs. The response returns the batch backup metadata and bounded per-pair statuses/revisions/codes plus summary counts, without save bytes, player identities, or inventory dumps. Repeating the endpoint is safe because delivered profiles carry durable receipts. The batch's status and each non-delivery reason are logged. IPS association remains diagnostic only and cannot disqualify a save.

The save bytes and metadata are two files today, so the event write creates a durable original-save backup and a per-save journal before replacing either file. The save store checks the written bytes and receipt under its lock; a failed or interrupted replacement rolls back to the original from the journal on the next read or write. A dead process's save lock is reclaimed by checking its recorded PID. The delivery service rereads the stored save and receipt before reporting success. A receipt is trusted only when its metadata passes validation. A normal save advancing to a new revision preserves it. Explicit old-save restoration, profile movement, or ROM re-binding still need an operation-specific receipt reconciliation path before those operations are offered; the current generic save PUT does not distinguish an ordinary in-game save from a manually restored old one. Do not rely on the assumption that Key Items are impossible to remove: the original gift scripts explicitly contemplate moving a full Key Items pocket's contents to the PC. A receipt records successful delivery to a save lineage, not a perpetual assertion about current Bag contents.

Automated tests cover all eight FireRed/LeafGreen combinations of League, National Dex, and Network Machine state; Ruby/Sapphire League-only eligibility and National Dex upgrade with Eon Ticket in one backed-up revision; preservation of an already unlocked Dex display choice; Emerald's unchanged gate; partial National Dex state; candidate byte allowlists; unsupported titles; already-owned items; PC-only conflicts; full pockets; idempotence after receipt; lease races; backup failure; and a process exit between save-byte and metadata replacement. The service is connected after completed player close and through the authenticated manual batch route, with no new UI. Batch tests must prove authorization, full-backup-before-first-write, no write on backup failure, sequential attempts, lease deferral, continuation after per-pair failure, and repeat idempotence. Still required for user acceptance: disposable saves loaded in EmulatorJS to prove National Dex display, Key Item visibility, ship destinations, encounters, and Mystery menu behavior; exact ROM revision/language compatibility; and explicit old-save restoration/profile movement handling.

## Gabby and Ty stationary rematches (2026-09-30)

On each completed player close, the existing optional Gen III delivery attempt checks Ruby, Sapphire, and Emerald for the Gabby and Ty battle counter **only after the save's `gameClear` flag proves the League and Champion were defeated**. Their original game code stores `battleNum` as a saturating `u8` in SaveBlock1: logical large-block offset `0x2B19` in Ruby/Sapphire and `0x2BAD` in Emerald. At `0xFF`, the game selects their final Route 111 appearance and keeps the counter there. The recipe sets that byte to `0xFF` and reconciles only the eight Gabby/Ty hide flags so the final Route 111 pair is visible and the other appearances are hidden. This permits immediate, consistent rematches even when the pair was on another route before the edit. It changes no other flags, trainer progress, Pokémon, or inventory.

League completion is required for this adjustment; the National Dex and ticket gates are independent. In Emerald, the adjustment can run after the League even while the ticket bundle waits for the National Dex. It uses the verified ROM identity, unambiguous save-copy selection, exact byte-change validation, lease and revision checks, backed-up journaled save-store write, readback, and runtime-state invalidation already used for event delivery. The receipt may initially contain the adjustment ID with no delivered ticket event IDs; a later eligible close can still deliver the tickets and preserve that adjustment marker. Existing receipts migrate once on a later completed close after League completion or through authenticated manual reconciliation with that same gate. A recorded marker prevents reapplying the adjustment to subsequent player saves, even if gameplay later changes the saved byte. Unsupported or malformed saves and failed attempts remain optional and cannot block the core close or launch flow.

## Questions deliberately left for later product decisions

## Package contracts

Given immutable save bytes and a trusted title/layout identity, inspection returns a bounded structured result: Key Items and PC slots, free counts, and explicitly requested event flags. It must return no Pokémon data, trainer name, or raw save bytes to clients or logs. Unknown title, equal-index conflicting copies, malformed inventory for an edit, or unsupported flag mapping rejects explicitly rather than guessing offsets. The package tools cannot verify ROM bytes; the backend obtains the title from its catalog and checks the actual ROM's SHA-256 before using them.

The **pure byte editors** in `apps/packages/` take original bytes and a narrowly scoped item or flag operation and return a new byte buffer or a typed rejection. They never mutate the input. They are idempotent, preserve every unrelated byte, write only missing items to verified free Key Items slots, and update only explicitly requested flag bits in the selected valid copy plus affected checksums. They then reparse and verify the result. Insufficient capacity rejects before writing. No writes to the inactive copy, ROM, runtime RAM, Party, Pokémon PC, or money. The generic flag tool can change any supported flag passed by a trusted caller; the event policy restricts IDs and sets a flag only when the associated delivery state is consistent. Exact recipes and handling of pre-existing partial states still require disposable-save verification.

The backend integration re-reads the canonical save under exclusive ownership, compares the expected save revision, retains a recoverable preimage, writes through the atomic save store, and applies the Spec 070 runtime-state invalidation barrier. A failed preflight or conflict leaves the canonical file, revision, leases, and runtime states unchanged. An optional event integration never becomes a ROM/profile/lease launch prerequisite.

## Package implementation: independent tools and a pure event grant

The independent modules in `apps/packages/` are `pokemon-gen3-event-flags.mjs` for persistent flag bits and `pokemon-gen3-inventory.mjs` for Key Items inspection/insertion; neither depends on the other. `pokemon-gen3-event-eligibility.mjs` reads the title-specific progression gate without editing save bytes; `pokemon-gen3-national-dex.mjs` performs the narrowly scoped Ruby/Sapphire upgrade; `pokemon-gen3-event-grant.mjs` composes those tools for a selected Generation III catalog event set. `pokemon-gen3-event-candidate-validation.mjs` validates the private candidate, and `pokemon-gen3-event-delivery.mjs` coordinates the backend grant after a completed player close. Shared sector addressing, save-copy selection, and checksum repair live in `pokemon-gen3-save-validation.mjs`. All APIs take a trusted `pokemonSaveTitle` associated with the verified ROM. Save bytes alone cannot be assumed to prove the title or ROM revision.

### Independently checked byte facts

| Title family | Large-block event flag base | Flag bytes | Key Items offset in large block | Key Items slots | PC items offset / slots | Bag quantity XOR key |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Ruby/Sapphire | `0x1220` | 288 | `0x5B0` | 20 | `0x498` / 50 | none |
| Emerald | `0x1270` | 300 | `0x5D8` | 30 | `0x498` / 50 | low 16 bits of small block `0x0AC` |
| FireRed/LeafGreen | `0x0EE0` | 288 | `0x3B8` | 30 | `0x298` / 30 | low 16 bits of small block `0xF20` |

These are logical SaveBlock offsets, **not** absolute file offsets. A large-block byte at offset `n` lives in logical section `1 + floor(n / 0xF80)` at local offset `n % 0xF80`; the validated section map locates that section's physical 4 KiB sector. Section 0 holds the small block. A slot is four little-endian bytes: item ID `u16`, quantity `u16`. PC item quantity is not XOR encoded. A free Key Items slot has item ID zero; its quantity bytes may contain an encoded zero, so free-slot detection must use the ID and overwrite both fields on insertion. A populated Key Item slot must decode to quantity one for this initial writer. The original-game IDs are **the same across Ruby, Sapphire, and Emerald where an item is defined**: Eon Ticket is `275` in all three. Ruby/Sapphire do not define the other three tickets. Emerald additionally defines MysticTicket `370`, AuroraTicket `371`, and Old Sea Map `376`. FireRed/LeafGreen define MysticTicket `370` and AuroraTicket `371`. The first writer permits only those item/title combinations; extending it requires reviewed title metadata.

The Generation III encounter JSON records `itemIdByTitle` for each event rather than assuming an ID from its name or a cross-game item table. It records the Key Items and PC item logical offsets, capacities, four-byte little-endian slot format, requested quantity one, and Emerald/FireRed/LeafGreen small-block quantity XOR key offsets. To insert, validate the save and title, inspect Bag and PC for that exact ID, count missing items and free Key Items slots, reject conflicts or lack of space, write the ID and encoded quantity into a free slot of the selected copy, update the affected section checksum, and revalidate. The numeric IDs in the JSON are factual ROM item constants; adding an item does **not** by itself set the event access flags or establish that the harbor will offer a destination. The JSON supplies data to the current orchestrator; the inventory package has its own explicit allowlist and a test checks that its behavior agrees with the catalog.

For Emerald and FireRed/LeafGreen, the port scripts require the relevant item in the Bag **and** its ship flag. The detailed recipe table above distinguishes those flags from global Mystery menu unlocks, receipt flags, first-display flags, and encounter-completion flags. The generic flag tool must not hard-code the event recipe. Eon Ticket receipt has a different path in Ruby/Sapphire and Emerald. Region/language compatibility and in-game prerequisites remain future integration checks.

### Ruby/Sapphire National Dex editor contract

- `enableRubySapphireNationalDex(saveBytes, pokemonSaveTitle)` accepts only Ruby or Sapphire and requires the validated active copy's game-clear flag. An already complete National Dex returns equal bytes without changing the player's Pokédex mode or order. Otherwise it writes the reviewed magic, variable, National Dex flag, mode, and order; it preserves the original buffer and inactive copy, repairs affected checksums, and verifies the existing adapter's National Dex predicate.
- The event materializer applies this editor only after the Ruby/Sapphire League gate and before adding the Eon Ticket. The independent candidate validator permits precisely those fields only when the original lacked a complete National Dex. Emerald and FireRed/LeafGreen still require their preexisting upgrade and never pass through this editor.

### Flag tool contract

- `readPokemonGen3Flags(saveBytes, pokemonSaveTitle, flagIds)` returns an ordered boolean result for explicitly requested integer flag IDs. `editPokemonGen3Flags(saveBytes, pokemonSaveTitle, changes)` accepts an array of `{ flagId, value }` where `value` is a boolean and returns a new 128 KiB `Uint8Array` with the requested bits changed. No mutation of the input. Duplicate IDs, out-of-range IDs, invalid types and unsupported titles reject before writes.
- Read and modify only persistent large-block flags. The valid range is `0..(8 * flagBytes - 1)` for the title. Preserve all unrelated bits in the same byte. An unchanged edit returns an equal-byte copy; setting an already set bit is idempotent.
- The interface is a byte primitive for trusted package/backend callers, not a public API for arbitrary client-selected flags. The event policy decides which flags to pass.

### Inventory tool contract

- `inspectPokemonGen3Inventory(saveBytes, pokemonSaveTitle)` reports Key Item slots and free count, plus PC item slots, without trainer or Pokémon data. It reads quantities using the title's encoding and does not mutate bytes.
- `addPokemonGen3KeyItems(saveBytes, pokemonSaveTitle, itemIds)` returns a new 128 KiB `Uint8Array`; it adds one of each requested supported event item to free Key Items slots. Duplicate request IDs, unsupported item/title combinations, malformed occupied Key Item quantities, duplicate existing Key Item IDs, and insufficient free slots reject before writes. An item already in the Bag is left untouched. An item found only in the PC rejects rather than creating a duplicate; the player can move that item in the game before a future delivery attempt. No sorting, compaction, removal, PC mutation, other-pocket mutation, or quantity increase is in this slice.
- Existing slot order and all unrelated bytes remain intact. Key Item capacity is finite despite normally ample room. The full-pocket case is a validation failure, never permission to overwrite a slot.

### Shared integrity and test gates

All pure editors use the existing strict 128 KiB/sector checksum validator, select the newest valid copy, and reject two valid copies with the same save index but different logical data. If both copies are identical, inspection may use the first; a changing edit rejects because modifying one copy would make the result ambiguous. If only one is valid, use it. Edits clone the input, change only bytes in the selected copy, recalculate only affected section checksums, and revalidate the result. Preserve the older/inactive copy, sector IDs, signatures, save indexes, trailing sectors and all other bytes. A failed edit produces no output buffer and leaves the caller's input unchanged. The pure event materializer composes the applicable tools on private buffers; the backend delivery service publishes their combined result through one journaled save-store write.

Tests use synthetic fixtures with scrambled physical sector order and two copies. They cover all five titles, nonzero XOR keys, encoded empty slots, already-owned and PC-owned items, full pocket, malformed occupied quantities, duplicate items/flags, first and last valid flag IDs, unrelated bits in a shared flag byte, wrong lengths/checksums, one invalid copy, conflicting equal-index copies, idempotence, and exact byte-diff allowlists. At least one disposable save still must be loaded in EmulatorJS for each title before in-game behavior is considered verified; synthetic checksums alone cannot prove ticket visibility or ship access. No real user saves enter tests or Git.

## Verification required for in-game acceptance

1. Pin primary source revisions and independently map each supported title's Bag, PC item and flag offsets, item IDs, quantity encoding, security key, capacities, event prerequisites, and section boundaries. Distinguish factual offsets from product policy.
2. Obtain or generate consented, non-production fixtures for each exact supported title/region/revision: empty, partly full, full, item in Bag, item in PC, already completed encounter, partially set flags, both save copies valid, one copy invalid, equal-index disagreement, and boundary-crossing sector layouts. Do not commit real user saves.
3. Compare the inspector with at least one independent parser and verify behavior by loading disposable copies in the actual emulator. A parser agreement alone is insufficient for destination access.
4. For a candidate writer, assert byte-level allowlists and unchanged inactive copy; verify both sector checksums, full reparse, inventory count and item visibility, idempotence, ROM/game load, ship destination, encounter, and an ordinary in-game save/reload.
5. Exercise backend revision conflicts, active player and Hub leases, interrupted atomic write, stale runtime snapshot, retry and rollback using disposable profiles. Save preservation and recovery are acceptance gates.

## Suggested order of remaining work

1. Verify the existing read-only Bag/PC/flag inspector and byte editors against disposable real-game saves and each exact supported ROM identity.
2. Pin per-title event recipes and the ROM/language policy, then test actual ship access and encounters in EmulatorJS.
3. Validate disposable candidate saves in EmulatorJS and let the user confirm the Key Items and island events. Add explicit restore/rebind receipt reconciliation before offering those operations for event-modified saves.
