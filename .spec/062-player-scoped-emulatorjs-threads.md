# Spec 062 — EmulatorJS threads per player iframe

## Goal and decision

Enable the pinned EmulatorJS threaded mGBA core by default **inside each compatible `player.html` iframe**, while retaining the ordinary core for browsers and surfaces that cannot isolate that iframe. The hub page, catalog, covers, backend, and user preferences do not select or host the core. Every concurrent emulator makes its own capability decision before appending `loader.js`.

This is one specification containing the current-state survey, implementation plan, and acceptance criteria. It does not authorize a build, commit, deploy, or change to existing save/snapshot semantics.

## Technical basis and limits

- [EmulatorJS documents `EJS_threads`](https://emulatorjs.org/docs/options/#ejs_threads) as a boolean defaulting to false and says it *may* improve performance. The documented COOP/COEP route describes traditional page-wide isolation; it is not the only browser mechanism now available.
- [Chrome's Document Isolation Policy](https://developer.chrome.com/blog/document-isolation-policy) permits `crossOriginIsolated` on one iframe without isolating its parent. The official announcement identifies Chrome 137 desktop support; availability on other browsers and devices must be determined at runtime, not assumed from a user agent string.
- Serve `Document-Isolation-Policy: isolate-and-require-corp` on the player document only. Cross-origin player subresources must be CORS-enabled or explicitly allow cross-origin embedding. Audit the exact pinned CDN scripts, threaded core data, worker/WASM loading, and any other resource the player actually fetches. A successful HEAD response alone does not prove the worker boot path works in a browser.
- The hub page remains unisolated. Its external catalog cover requests are irrelevant to the player document's resource policy. Do not proxy covers, add COOP/COEP to the hub, or change catalog rendering for this feature.
- Inside an HTTP(S) `player.html`, enable threads only when `window.crossOriginIsolated === true`, `typeof SharedArrayBuffer === 'function'`, and `launch.core` is the verified GBA core. The pinned threaded asset must be published and actually start; a download/start failure falls back once. Assign `window.EJS_threads` before `loader.js`. Set it explicitly false otherwise. Do not treat a `SharedArrayBuffer` property alone as sufficient proof of isolation.
- The pinned 4.2.3 runtime has a distinct `mgba-thread-wasm.data` asset. Its existence establishes that a threaded build is published; it does **not** establish a performance gain, state-file compatibility, or support on every browser.
- [Emscripten's pthread documentation](https://emscripten.org/docs/porting/pthreads.html) distinguishes pthread support from moving the application main loop to a worker. This project must measure the actual result; it cannot promise that `getState()`, `getSaveFile()`, React, or all emulation work leave the UI thread.

## Player/parent boundary under isolated documents

The [Document Isolation Policy behavior](https://developer.chrome.com/blog/document-isolation-policy) permits `postMessage` but removes synchronous DOM access between an isolated iframe and a nonisolated same-origin parent. Therefore the parent must not depend on `iframe.contentDocument` or functions exported on `iframe.contentWindow`, even when those accesses currently work in the fallback mode.

| Existing operation | Current code | Required contract |
| --- | --- | --- |
| Fast Forward message overlay | `configurePlayerFrame()` in `main.jsx` reads `contentDocument`, installs a `MutationObserver`, and hides `.ejs_message`. `player.js` also has `hideFastForwardOverlay()`, but currently calls it during normalization. | The player owns observation of its own `#game` DOM for subsequent overlay changes. Parent only sends Fast Forward state. Remove parent DOM access and duplicated observer bookkeeping. |
| Interaction lock | `main.jsx` calls `emulatorHubSetInteractionLock()` directly when available; the message fallback has no acknowledgement. | Parent sends session-addressed lock/unlock request; player acknowledges application. The chooser and opaque save overlay must not permit gamepad, keyboard, L2, or R2 input while a lock is pending. A delayed unlock cannot reopen input during a newer lock. Preserve the preexisting pause state. |
| Close/save flush | `flushPlayerSave()` prefers direct `emulatorHubClose()` and already has a 30-second `emulator-hub:save-synced` response to its message fallback. | Use the message path consistently. Keep request ID, origin, source, timeout, error, retry, and `preserveRecovery` behavior. Do not release a lease or unmount an iframe before acknowledged save completion. |
| Local recovery clear | `clearPlayerRecovery()` prefers direct `emulatorHubClearLocalRecovery()`; its message fallback resolves immediately, while the player performs asynchronous deletion without replying. | Add request ID and success/failure reply. Wait for the reply in the same place the direct promise is currently awaited. On failure, use the existing close/error policy; do not silently report deletion complete. |
| Other commands | Focus, gamepad, reset, odds, mute, manual state actions, restore choice, and Fast Forward already use messages. | Preserve session, game, profile, request ID, source, and same-origin routing; verify each after isolated launch. Do not broaden state semantics. |

All per-player replies must be correlated to that iframe/session. A late reply from a removed or restarted iframe cannot satisfy a new request. The exact shared message contract should live in `apps/packages/` if more than one application module owns its validation, per project boundary rules.

## Launch and fallback plan

1. Add an exact `/player.html` location in production Nginx that serves the HTML and emits `Document-Isolation-Policy: isolate-and-require-corp`. Add equivalent player-document-only handling to Vite development serving. Check the header on the actual HTML response, not on `/index.html`, API, images, or the SPA fallback.
2. In the player, after authenticated launch metadata and before `loader.js`, evaluate the frame capability and eligible core. Keep one immutable per-launch decision; neither parent preferences nor a later UI update may hot-swap a running core.
3. When eligible, set `EJS_threads = true`; otherwise set it false and record one concise decision diagnostic (`selected`, `fallback`, reason, core, isolation status). Avoid periodic success logs. If a threaded asset or worker fails before `EJS_onGameStart`, retry once with the ordinary core **within the same session/lease** and without writing a snapshot. Preserve the pending restoration decision and canonical `.sav` preflight. Do not loop; if ordinary core also fails, surface the existing emulator launch error.
4. Keep the hub's catalog, external covers, profile picker, and normal page headers unchanged. The parent may change only its player messaging integration and iframe lifecycle handling. Keep surviving iframe keys and URLs stable during multi-emulator layout changes.
5. Electron remains on the ordinary core when its `file://` player is not isolated. A future Electron-specific isolation design requires separate validation and must not hold up the web fallback.

The automatic retry in step 3 needs a focused design check before implementation: clear only the failed, not-yet-started runtime; do not accidentally trigger `closeEmulator()` save synchronization or a recovery deletion. If the pinned loader cannot be safely retried inside one document, replace that step with an explicit **one-time iframe restart** retaining session/lease and restoration intent. This is a launch fallback, never an implicit save or snapshot action.

## Data integrity and behavioral invariants

1. The canonical `.sav` and runtime snapshots remain independent. Loading or saving a state does not write the `.sav`; only the game's own save changes it. Both core modes load the same canonical `.sav` after the existing restore choice.
2. Existing user state, local recovery, and cloud recovery must remain available according to the current rules. Validate state bytes produced by threaded mGBA when read by ordinary mGBA and the reverse, including a fresh session, before making threaded mode the default. If either direction fails, defer default enablement rather than silently dropping or consuming a candidate.
3. Automatic local capture, cloud capture, canonical save polling, backend revisions, discard delays, and manual state controls keep their current policy and interval. `EJS_threads` does not authorize a new snapshot on game save, launch, close, or fallback.
4. One player failure cannot disturb another iframe. A fallback affects only its session; all other emulator instances retain their running core, focus, controls, and state.
5. The optional thread feature must not weaken required ROM, profile, lease, save-integrity, or launch checks. A missing/invalid threaded asset selects the ordinary core; an invalid core ROM or missing required save still follows the existing hard failure path.

## Verification and rollout gates

- **Unit tests:** player-side eligibility matrix (isolated/unisolated, SAB present/missing, GBA/other core), single retry limit, one decision per iframe, message request/reply identity, stale replies, lock ordering, and no accidental save/snapshot action from fallback.
- **Frontend integration tests:** Nginx/Vite header scope; player launch configuration before loader; Fast Forward overlay owned inside the iframe; parent commands through messages; lock acknowledgement; close/save and local-recovery-clear acknowledgement; isolated iframe with multiple live players; canonical `.sav` and restore sequencing unchanged. Backend integration tests only if a backend contract actually changes; none is planned.
- **Browser validation for rollout, performed by the user:** on compatible Chrome desktop, inspect `/player.html` response header and `crossOriginIsolated` inside each frame, confirm threaded mGBA asset/worker and actual game start, try 1/2/4/6 instances with Fast Forward at 1.5× and 5×, and compare achieved emulated frames per wall-clock second plus long-frame/jank counts with the ordinary core. Repeat ordinary-core fallback on a browser without frame isolation and on Electron. Validate both directions of snapshot compatibility and canonical `.sav` integrity before switching the default.
- **Outcome gate:** do not state that threads fix multi-instance Fast Forward oscillation unless measured data show it. If they do not, keep this as an optional verified runtime capability and investigate remaining contention separately; do not change snapshot/save cadence again as part of this spec.

No end-to-end automation is requested; the user owns that test pass. No build, commit, or deploy without an explicit request in the task that performs it.

## Detailed implementation context and record

The checkout before this change had two Vite HTML inputs (`index.html`, `player.html`) and one Nginx SPA catch-all. A player receives an authenticated lease launch, ROM bytes, the canonical save and snapshot candidates, then writes the `EJS_*` globals and appends the pinned loader. The parent addresses its iframe through the immutable session ID in `.player-cell[data-session-id]`. This is the exact point for a per-player core decision; no React state or backend field is required.

The pinned EmulatorJS 4.2.3 `downloadGameCore()` selects `${core}${threads ? '-thread' : ''}${legacy ? '-legacy' : ''}-wasm.data`; its `startGameError()` sets `failedToStart`. Both `mgba-thread-wasm.data` and `mgba-thread-legacy-wasm.data`, plus the loader and mGBA report, returned HTTP 200 from the pinned CDN during the implementation survey. Its CDN responses included `Cross-Origin-Resource-Policy: cross-origin` and `Access-Control-Allow-Origin: *`. This is resource availability evidence, not browser-start or snapshot-compatibility proof. Its setting lookup does not override `EJS_threads` when this application's `EJS_disableLocalStorage = true`.

The implementation uses these boundaries:

1. Nginx sends the DIP header only from an exact `/player.html` location; the Vite dev/preview middleware applies it only when the request path is `/player.html`. Neither the hub page nor catalog resources are changed.
2. `apps/packages/player-thread-policy.mjs` decides threaded versus ordinary mGBA from the player document's scheme, isolation, shared-memory availability, core, and one-time fallback marker. `player.js` sets `EJS_threads` before appending `loader.js`. A failure detected before `EJS_onGameStart` reloads that iframe with `threadFallback=1`, preserving the existing game, profile, session and lease parameters. The next load uses the ordinary core. Once the game has started, the fallback cannot reload it.
3. `apps/packages/player-frame-request.mjs` correlates parent requests by origin, source WindowProxy, session ID and request ID. Close/save synchronization and local recovery deletion use this acknowledgement path. The player confirms lock application with a monotonic revision so a late unlock cannot reverse a newer lock. The parent no longer reads the player's DOM or calls its exported methods synchronously; the player observes its own Fast Forward overlay. Existing snapshot candidate and canonical `.sav` flows remain in `player.js`.
4. A local recovery clear timeout/failure is logged under the existing close policy; it does not falsely count as confirmed deletion. The canonical save must be confirmed before the lease release. No new state capture or `.sav` write occurs in thread selection or fallback.

Automated coverage includes selection/fallback unit tests, per-frame request correlation, player message acknowledgements, header scope, close/restore regression tests, and frontend lint. Browser verification remains necessary for actual DIP activation, threaded worker startup, multi-instance Fast Forward throughput, and state compatibility in both core directions. Those outcomes are not inferred from source inspection or unit tests.

After the implementation, the frontend test suite, shared-package suite and deployment-configuration tests pass, and frontend ESLint reports no issues. No project build was run. The two existing skipped package tests remain skipped. The user will run the browser/device end-to-end checks before this behavior is considered proven in production.

## Per-player FPS diagnostic (`VITE_DEBUG=1`)

The frontend already reads `import.meta.env.VITE_DEBUG` through `getClientDiagnosticsOptions()` in both hub and player. `apps/frontend/.env.example` documents `VITE_DEBUG=0`; setting it to `1` enables the existing diagnostics. No second environment variable or parent-page FPS calculation is needed.

The pinned 4.2.3 `GameManager.getFrameNum()` wraps the core's `get_current_frame_count`. The player already reads it for a two-sample startup stall check (`apps/packages/emulator-frame-progress.mjs`). For an ongoing display, each debug-enabled player samples its own counter and `performance.now()` once per second after runtime readiness. The counter delta divided by actual elapsed wall-clock time is **emulated frames per second**, not browser-rendered frames per second. A GBA's nominal frame rate is `16_777_216 / 280_896 ≈ 59.7275`; the measured multiplier is observed FPS divided by that rate. Show the observed multiplier beside the player's requested Fast Forward speed so `5×` is visibly distinguishable from the measured result.

The badge belongs to the `player.html` document and is positioned above that iframe's game viewport. It does not intercept pointer/keyboard/gamepad input and does not send a diagnostic event every second. A missing or reset frame counter yields an unavailable reading and resets the sample baseline; a paused emulator may show zero. Start only when `VITE_DEBUG=1` and game runtime readiness is established. Stop the interval on the existing player close path; browser iframe destruction also disposes it. This display changes no Fast Forward, snapshot or canonical save behavior.

## Chrome multi-player performance investigation — 2026-09-24

This is a source/artifact investigation, not a browser benchmark or approval of a new architecture. The user observed approximately 5× each with two players, 2.8–2.9× with three, 2.3–2.5× with four, 1.5–2.0× with five, and 0.9–1.2× with six in Google Chrome. Chrome reportedly used about 300 MB for one and 1.4 GB for six. CPU/GPU specifications, active worker counts, renderer PIDs and performance traces were not supplied. No cause or performance gain has been experimentally established.

Both threaded JS variants contain `pthreadPoolSize=4`, preallocate workers with `new Worker(pthreadMainJs,{name:"em-pthread"})`, and initialize shared WASM memory at 134,217,728 bytes (128 MiB). `getNewWorker()` can allocate another worker when the pool is empty: four is a preallocated pool, not a hard active-thread limit. The ordinary variants lack this pthread pool. The inspected threaded metadata identifies build version `2.0.2`, minimum EmulatorJS `4.2.2`, and the `EmulatorJS/mgba` repository; it does not pin every source/build flag.

**Correction to a possible reading of the earlier worker discussion:** these published archives have no separate `.worker.js`. Their generated JS reuses its own script/blob as the worker entry point. Looking only for a network filename ending in `.worker.js` would produce a false negative. Six successfully initialized threaded players normally precreate 24 workers, which may be idle. Shared memory is shared within one player's pthreads; do not multiply its 128 MiB initial heap by four workers or equate reserved maximum WASM address space with physical RAM.

Pinned [emulator.js](https://cdn.emulatorjs.org/4.2.3/data/src/emulator.js), lines 592–603, selects the threaded/legacy filename; lines 939–975 instantiate `EJS_Runtime` in the document; line 987 calls `Module.callMain`. Historical upstream [Makefile.emulatorjs](https://github.com/EmulatorJS/RetroArch/blob/6b8285fbe4474c87e2b8a3222d431e52ce05f8b5/Makefile.emulatorjs#L85) separately defaults `PROXY_TO_PTHREAD` to zero. Its [build script](https://github.com/EmulatorJS/RetroArch/blob/6b8285fbe4474c87e2b8a3222d431e52ce05f8b5/emulatorjs/build-emulatorjs.sh#L74) sets a four-worker pool for `--threads` without selecting that proxy option. [Emscripten pthread documentation](https://emscripten.org/docs/porting/pthreads.html) distinguishes pool creation, main-thread proxying, and synchronization; busy waits/proxy overhead can consume capacity even when useful work is limited.

### DIP does not allocate one execution lane per iframe

[Chrome's DIP documentation](https://developer.chrome.com/blog/document-isolation-policy) establishes per-document shared-memory eligibility and removes synchronous DOM access between isolated and nonisolated documents. It does not promise a separate process or CPU core for every same-origin iframe. Chromium's [AgentClusterKey implementation](https://chromium.googlesource.com/chromium/src/+/refs/tags/142.0.7444.138/content/browser/agent_cluster_key.h) keys isolation using origin and isolation status and documents shared SiteInstances for matching keys within a BrowsingInstance. Different session query strings are not different origins.

Consequently the same-origin isolated players can remain grouped together, separately from the unisolated hub. This is a concrete reason to check shared renderer/main-thread contention first. The referenced Chromium revision explains the mechanism; actual PIDs, agent behavior and scheduling on the user's installed Chrome have not been inspected. Adding `Origin-Agent-Cluster` to otherwise identical origins is not per-player isolation.

### Quantitative interpretation

The badge measures emulated frame-counter progress per actual elapsed wall time, not display refresh. Using the nominal GBA rate of about 59.7275 FPS:

| Players | Reported speed/player | Approximate sum of speeds | Approximate total emulated FPS | Fraction of aggregate 5× target |
| --- | --- | --- | --- | --- |
| 2 | near 5× | near 10× | near 597 | near 100% |
| 3 | 2.8–2.9× | 8.4–8.7× | 502–520 | 56–58% |
| 4 | 2.3–2.5× | 9.2–10× | 549–597 | 46–50% |
| 5 | 1.5–2.0× | 7.5–10× | 448–597 | 30–40% |
| 6 | 0.9–1.2× | 5.4–7.2× | 323–430 | 18–24% |

These are approximate envelopes derived from the user's ranges, not synchronized aggregate samples or confidence intervals. Two capped players do not reveal uncapped machine capacity. Three to five broadly resemble division of a limited shared budget. Six appears to lose aggregate throughput as well: compatible with contention/scheduling, rendering, memory/GC, thermal limits or workload differences. It does not prove RAM exhaustion, GPU saturation, all CPU cores saturated, or worker oversubscription. Six at 5× would require about 1,792 emulated FPS, roughly 4.2–5.6 times the observed six-player aggregate.

| 3. Rendering/compositing/audio overhead | More canvases and presentation paths share hardware. Inspect GPU/renderer tracks and actual hardware/software WebGL; vary canvas size/shader cost while keeping all frames visible and emulation identical. Compare mute cautiously: gain-based mute need not stop audio processing. | If presentation dominates, test reduced shader/pixel workload or presenting fewer frames while emulation continues. Do not use hiding/minimizing as the sole test: browser throttling changes scheduling. Skipping emulation steps is not an equivalent optimization. |
| 4. Synchronous save/state work and allocation bursts | Core state/save calls are synchronous; six players average one periodic state extraction/second plus two save checks/second. | 5. Repeated input/UI/debug overhead | Up to 375 messages/second at six players, but core input is already transition-only; observers do not watch canvas drawing. Measure task durations and mutation frequency. | 6. Memory pressure/GC/power/background policy | 1.4 GB is an observation, not evidence of exhaustion; shared 128 MiB heaps and renderer overhead explain a baseline without proving the remainder. Correlate hard faults/available RAM, GC, GPU memory, CPU frequency, visibility and Chrome power settings with dips. | Fix the measured pressure or power condition. Do not infer a leak from comparing one vs six instances, or disable browser security features to chase throughput. |

For a main-thread cost budget, if all six share one execution lane, periodic extraction occupying `T` milliseconds per capture at one capture/second averages `T/1000` of that lane; save checks at two/second with duration `S` add `2S/1000`. This makes the hypothesis falsifiable: small measured callback totals cannot explain a sustained several-fold deficit, though bursts can still cause visible hitches. Simultaneous captures require peak analysis as well as averages.

Community reports are useful leads, not proof here. [EmulatorJS #1255](https://github.com/EmulatorJS/EmulatorJS/issues/1255) reports WebGL alpha/compositing effects using 4.2.3, but its quantified experiment used an NGP core and headless Chromium/SwiftShader, not this desktop mGBA setup. [mGBA #2549](https://github.com/mgba-emu/mgba/issues/2549) describes choppy native Qt Fast Forward while game speed remained correct; it illustrates the difference between presentation FPS and emulated throughput and does not explain this counter-measured slowdown. No verified upstream report establishes that six 5× mGBA players should work on this unknown machine.

**Recommendation at investigation time:** identify the runtime and measure multi-player throughput with a representative trace before changing architecture. A separate ordinary/threaded comparison can follow if the measurements warrant it. Moving one emulation owner per player onto a worker or distinct renderer execution context is only a candidate if the trace confirms serialized core work with spare CPU. Decide between alternatives after seeing the trace, with explicit save/recovery compatibility and responsiveness gates. If the shared bottleneck is GPU, hardware capacity or periodic synchronous work, follow the corresponding narrower path instead. This paragraph records the earlier source investigation; the automated development harness below was implemented afterward.

## Intensive development-mode bottleneck protocol — 2026-09-24

This protocol investigates the measured collapse from approximately 5× with two players to 0.9–1.2× with six. It is a sequence of **experiments**, not a finding that threads, Chrome, snapshots or hardware are at fault. Keep the raw readings and trace from each phase; change one factor at a time and proceed to an architectural proposal only when a candidate explains the measurements. The user performs browser end-to-end trials; code instrumentation, if needed, is a later, explicit development task in this same spec.

### Preparation and comparability

1. Set `VITE_DEBUG=1` in `apps/frontend/.env` and restart the development server so every player shows its measured emulated FPS and multiplier. Confirm that the badge reads roughly 59.7 FPS at normal 1× on one running GBA before trusting its 5× readings. The badge is not the Chrome display FPS.
2. Use disposable test profiles and a fixed ROM, save position and in-game scene. Keep requested Fast Forward at 5×, viewport and canvas dimensions, shader, audio setting, controller connection, Chrome window position, monitors and foreground visibility identical across trials. Record the ROM/core version, Chrome version, Windows power mode, CPU physical/logical cores, RAM, GPU, hardware acceleration and `chrome://gpu` status. Do not use a hidden/minimized window as a performance comparison because visibility can change browser scheduling.
3. Record the baseline *without a DevTools Performance recording*. With `VITE_DEBUG=1`, the frontend detects six ready player frames, waits 20 seconds, records 60 seconds automatically and emits one aggregate report to the browser console. It samples each player's actual multiplier once per second and reports median, low tenth percentile and simultaneous aggregate speed. Other player counts can be compared separately after the six-player bottleneck is understood. Repeat controlled runs with the same scene and use upward/downward player counts to expose startup, thermal or power drift. A single visual glance at the FPS badge is insufficient for a small difference. There is no per-sample console or backend log.
4. ### Gate 1 — establish what Chrome is actually executing

Before measuring threaded versus ordinary speed, inspect **each** player's `/player.html` execution context and actual HTML response. Record `crossOriginIsolated`, `typeof SharedArrayBuffer`, `EJS_threads`, `EJS_emulator?.config?.threads`, core name, startup state, shared WASM heap and any `threadFallback=1` marker. Confirm the selected archive (`mgba-thread-wasm.data` or ordinary variant) in Network, cached assets or Sources. In Sources > Threads, count created `em-pthread` workers and, in a trace, distinguish active work from idle pooled workers. The threaded archive has no separate `.worker.js` network request. Mark a trial invalid if a player silently fell back, never reached runtime readiness, used a different core, or has an unexpected speed setting. A shared heap and four pooled workers per player prove initialization, **not** that the emulation loop is parallel.

### Gate 2 — controlled core A/B

If the automatic six-player report and a Chrome trace point to threaded-core overhead, make a separate diagnostic code change for a controlled ordinary/threaded A/B under the **same** player-document isolation, ROM/scene and presentation settings. Repeat each arm three times, alternating order. Record aggregate speed, slowest player, per-process CPU/memory, number of created versus busy workers and errors. The current automatic harness leaves core selection untouched; no query parameter or manual core switch is part of this stage. A future comparison must launch each player safely under its normal session/lease and verify the active core after launch.

Interpretation gate: if ordinary consistently improves the six-player aggregate while workers mostly wait, investigate threaded overhead; if threaded improves it, preserve that evidence but continue looking for remaining contention; if both show a hot shared renderer main thread with spare logical processors, test the execution-lane hypothesis; if useful work already fills available CPU, a worker/process rearrangement alone cannot provide 30× aggregate target. Treat an A/B difference as actionable only if its direction repeats across runs and exceeds run-to-run variation; do not select a new default from a single run.

### Gate 3 — locate time on the CPU/GPU timeline

For the representative 3- and 6-player cases, capture a separate 60-second [Chrome DevTools Performance trace](https://developer.chrome.com/docs/devtools/performance/overview) with CPU throttling off. Compare its speed with the unrecorded baseline because the profiler itself adds cost. Check which frame/renderer and workers the recording contains; profile another target if the trace omits a player. Attribute hot samples to document main thread, WASM core, active pthreads, gamepad message handling, rendering/compositing, audio, GC, `getState()` and `saveSaveFiles()`. Inspect total/self time and longest tasks, not only a colorful flame chart. Do not pause on breakpoints or perform a console evaluation during timed samples. Where possible, export the trace with a trial ID.

The 60-second window includes multiple 3-second save checks, 10-second local captures, 15-second cloud captures and two 30-second coincidences. Correlate dips in the emulated-frame counter with those timestamps. A long HTTP/IndexedDB promise is not blocked main-thread time. If call stacks do not expose the application's boundaries, add debug-only `performance.mark/measure` or aggregate timings around `saveSaveFiles`, `getState`, byte copying and message dispatch in `apps/frontend/src/player.js`, the canonical poller in `apps/packages/emulator-save-poller.mjs`, and the parent gamepad sender in `apps/frontend/src/main.jsx`. Report summaries every 30 seconds or on failure, without per-poll log spam. Instrumentation must preserve the existing save, recovery and lease ordering.

### Development harness requirements and implementation scope

- Existing `VITE_DEBUG=1` and per-player frame counter are the only activation path. No query parameter, console command, stored preference or manual core switch is introduced. Core selection and normal launch semantics stay unchanged.
- The hub recognizes six **ready** player frames from their valid frame-counter samples. It waits 20 seconds for warmup, captures 60 seconds, and writes one report with `console.log`. - Each debug player emits at most one sample per second using its existing frame-counter sample. The parent accepts it only from the expected same-origin iframe/session and keeps bounded memory. - Timing probes surround existing synchronous calls without changing their order, return values, exceptions, intervals or save/snapshot conditions. The parent gamepad measure covers its own poll/broadcast work and is kept separately from each player's core timings. The recorder's overhead is checked by comparing a debug run with the recorder idle versus active.
- Unit tests cover automatic six-player readiness, warmup/capture timers, invalidation on iframe reload, bounded samples, timing-drain reset, invalid/foreign frame rejection and unchanged save poll behavior. Existing save, snapshot, launch and input tests remain regression gates. No backend endpoint, stored preference or new core setting is added.

With `VITE_DEBUG=1`, a six-player report appears automatically in the hub browser console under `[emulator-performance]` after 20 seconds of warmup and 60 seconds of capture. The user controls when and how to run the development environment; this instrument does not ask them to execute console commands.

### Bottleneck and process-isolation options — 2026-09-24

The user observes that native mGBA can sustain roughly 10× with ten instances on the same Windows machine, whereas six browser players fall far below the 5× target without saturating total CPU or system memory. The traces explain the apparent contradiction: all six same-origin player iframes share one Chrome renderer process and one renderer main thread. That thread consumed 0.948 and 0.950 CPU-core equivalents in the threaded and ordinary captures, respectively. The six EmulatorJS `MainLoop_setImmediate_messageHandler` callbacks occupied about 89% of its measured `RunTask` CPU in both. React/Hub execution, local snapshot and `.sav` polling, DOM layout and GC are not the dominant sustained load. This is a *serialized execution bottleneck*, despite unused machine cores; it does not prove that browser overhead alone explains the entire native-versus-web speed gap. The WASM symbols are stripped, and the trace does not separate mGBA emulation cycles from every EJS rendering/audio operation with certainty.

The current `Document-Isolation-Policy` on `/player.html` enables `crossOriginIsolated`/SharedArrayBuffer where supported, but does not give six same-origin iframes six independent renderer main threads. Emscripten `-pthread` permits additional workers; only an architecture such as `PROXY_TO_PTHREAD` explicitly moves application `main()` to a worker. The published EJS threaded mGBA asset created 24 workers across six frames but left the EJS main loops on the same saturated renderer main thread. Merely returning to that asset or packaging today's single-window HTML unchanged in Electron does not remove this proven serialization point.

There are two technically relevant architectural experiments, neither approved for rollout by this diagnosis:

1. **Browser process separation:** give each player a distinct origin **with effective DIP** and verify the actual renderer PID for each iframe. Different paths or six same-origin frames do not separate them. Distinct subdomains of one site *without* an isolation mechanism do not guarantee separate processes; with DIP, Chromium's cross-origin-isolation key is origin-based and may separate them even within one site. First prove that this Chrome instance actually assigns six renderer PIDs; do not infer that from origin names or `crossOriginIsolated` alone. A low-cost local topology test can use Hub `localhost:5174` and player origins `localhost:5175`–`:5180`, each serving the same frontend/backend through a dev proxy and DIP on `/player.html`. Browser cookies are shared across ports of one host, but IndexedDB is per origin, including the port. A minimal throwaway frame test can establish process topology without loading profile data; real players with active save/recovery are required for a performance result. If six PIDs are confirmed, compare *unprofiled* achieved emulated speed at one, two, four and six players under the same ROMs, scenes, display size, audio and 5× setting, with a warmup and an A–B–A same-origin/separate-origin sequence. Only if this raises throughput should the production design address allowed parent/player origins and `postMessage` target/origin validation (`main.jsx` and `player.js` currently require `location.origin`), backend API/ROM and patch fetch credentials/CORS, player-scoped DIP, per-origin IndexedDB recovery and EmulatorJS save namespace, stable mapping/migration across launches, and the current profile, lease, snapshot and canonical `.sav` invariants. Chrome's process count/memory overhead and any remaining GPU/audio contention must be measured rather than assumed away.
2. **Actual off-main-thread emulation:** investigate a supported EJS worker runtime or a custom mGBA/Emscripten build with the core main loop on a dedicated worker, plus OffscreenCanvas or explicit rendering/audio proxying where needed. A worker per player could parallelize even within one site, but the pinned EJS 4.2.3 integration currently expects document APIs and synchronous state/save/control hooks. This is a vendor/runtime integration change, not an `EJS_threads` switch. Prove `getState`, `loadState`, `getSaveFile`, pause/lock, gamepad/keyboard, fast-forward, audio, and WebGL behavior before choosing it. Preserve the independent `.sav` contract and snapshot byte compatibility.

Electron is a separate deployment path: its current `apps/electron/main.cjs` creates one `BrowserWindow` loading the same frontend and its same-origin iframes. A future multi-`WebContentsView`/web-embed design could give players separate renderer execution lanes while keeping one composed application window, but must verify actual renderer PIDs and measured speed; Electron itself still uses Chromium. Electron recommends `WebContentsView` over `<webview>`, and view bounds, focus/input, lifecycle, profile storage and IPC require their own design. This is not an automatic performance gain from packaging.

Reference documentation: [Chromium OOPIF process model](https://www.chromium.org/developers/design-documents/oop-iframes/), [Chromium Site Isolation and process reuse](https://www.chromium.org/developers/design-documents/site-isolation/), [Chrome Document Isolation Policy](https://developer.chrome.com/blog/document-isolation-policy), [Emscripten pthreads/PROXY_TO_PTHREAD](https://emscripten.org/docs/porting/pthreads.html), [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), and [Electron WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view).

Independent Astra review of both traces and Chromium source corrected the same-site caveat above. The Chromium [AgentClusterKey](https://chromium.googlesource.com/chromium/src/+/main/content/browser/agent_cluster_key.h) records a DIP cross-origin-isolation key, and [SiteInfo](https://chromium.googlesource.com/chromium/src/+/main/content/browser/site_info.cc) treats effective DIP as requiring a dedicated process where supported. This makes distinct *origins* with DIP the first candidate; a PID trace remains the acceptance test. `Origin-Agent-Cluster` alone is not a per-player process guarantee.

For a full browser implementation, keep the existing local-recovery IndexedDB on the Hub origin and inject an asynchronous storage adapter into `createLocalRuntimeRecoveryStore()` in the player. This avoids stranding old recovery records or scattering them by port/slot. `getInstallationIdentity()` also reads origin-scoped localStorage and would require the Hub's existing identity over a validated channel. The parent/player message boundary must validate exact origins, `event.source`, and session/revision identity instead of replacing `location.origin` with `*`. Preserve canonical `.sav` bytes, validation, lease generation, snapshot candidate identity, and the rule that `loadState()` never writes the `.sav`. In production, `server.mjs` sets a host-only `emulator_hub_device` cookie and player leases bind to that device ID; simply proxying `/api` on `p1`–`p6` subdomains would create different device identities. A production design must either send player API calls to the fixed Hub origin with credentials and an explicit CORS allowlist (including required preflight headers and exposed `ETag`), or broker calls through the Hub. Do not widen cookie scope merely for this test.

Proposed performance acceptance for the experiment, not a predicted gain: six distinct player PIDs first; then each player's median speed at least 4.75× and p10 at least 4.5× over comparable unprofiled 60-second runs. A repeatable aggregate gain of at least 2× would justify further work even if it misses 5×; six confirmed PIDs with at most 20% gain would direct investigation toward per-player WASM, scheduling, rendering and audio costs instead. DevTools tracing explains topology and hot functions but should not serve as the primary speed measurement because profiling changes load.

### Native player-origin implementation and public deployment contract

This section supersedes the temporary `playerProcessTest=1` activation described earlier as historical experiment context. The Hub URL needs no test query parameter. `apps/packages/player-origin-topology.mjs` parses exactly six distinct numeric ports, rejects the Hub's own port and unsafe non-local HTTP, and maps each slot to the same scheme and hostname with its configured port. `main.jsx` reads `VITE_PLAYER_PORTS` independently of `VITE_DEBUG`; an absent or invalid value selects same-origin players. Each new launch probes free player ports in parallel using a two-second, cookie-free, opaque `HEAD /player.html` request and picks the first reachable free slot. If none respond, it launches on the Hub origin. The port is retained with that player session across grid changes. This probe tests network reachability, not the returned status, DIP header, or Chrome renderer PID; deployment checks remain required. The cross-origin `hubOrigin` parameter inside the iframe is operational routing data and is validated against the player's hostname/scheme; the user-facing Hub URL has no feature flag.

For local development, `apps/frontend/scripts/dev.mjs` wraps Vite. It reserves six loopback HTTP proxies on `PORT+1` through `PORT+6` (or six explicitly configured `PLAYER_ORIGIN_PORTS` from `apps/frontend/.env`) before starting Vite, then passes their list through `VITE_PLAYER_PORTS`. If binding fails, it closes any proxies already opened, logs one warning, starts Vite without the port list, and leaves the core launch on the Hub origin. `npm run dev` invokes this wrapper. The former standalone `player-origin-proxy` npm command and page query switch are removed; the proxy module remains as a reusable local HTTP transport. `VITE_DEBUG` still controls only diagnostic instrumentation and FPS badges.

For production, `deploy/.env` may set `PLAYER_ORIGIN_PORTS` to six reachable HTTPS listener ports. `docker-compose.yml` passes it as a frontend build argument, `deploy/frontend.Dockerfile` exposes it to Vite as `VITE_PLAYER_PORTS`, and the built frontend selects player origins without hard-coded hostnames or ports. Because Vite embeds `VITE_` values at build time, changing the port list requires rebuilding the frontend image. Empty configuration retains the ordinary same-origin deployment. The backend and existing frontend containers do not multiply per player; the Caddy process publishes and routes six listener ports to the same frontend service. Identical hostnames across ports keep host-only device cookies usable on relative player API requests, while each port has distinct IndexedDB; the existing parent storage bridge retains local recovery on the Hub origin. Exact `postMessage` origin/source/session checks and the independent canonical `.sav` and snapshot contracts remain intact.

The public operator procedure is in `deploy/README.md`. `node deploy/print-player-caddy.mjs HOSTNAME PORT1,PORT2,PORT3,PORT4,PORT5,PORT6 [UPSTREAM]` validates the inputs and prints six Caddy site blocks plus Docker Compose TCP port publications. It does not edit an external Caddy project or assume this repository controls that project's Compose file. Operators merge and validate these fragments, retain their existing main/private listeners, confirm certificate/DIP/API/ROM behavior on every port, and only then deploy the frontend build with the matching port list. No DNS record is needed when the ports use the already configured hostname. This public contract replaces the earlier subdomain proposal; the production VPS's currently configured 8444–8449 routes are one deployment instance, not a mandatory setting for other users.
